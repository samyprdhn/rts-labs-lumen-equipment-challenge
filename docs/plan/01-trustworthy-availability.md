## Problem (in business terms)

Lumen runs 12 jobsites on a shared fleet of ~60 cranes, excavators, lifts and dozers, currently scheduled on a spreadsheet. Dana loses real money ("about $38k in idle labor") when equipment shows as free but isn't — either because it's actually booked or because it's in the shop. Marcus needs to trust the same screen on a phone, with gloves on, in sunlight, and needs to know immediately, not later, when he's lost a race for a machine. Priya needs certified operators on cert-required equipment and needs operator PII locked down to people who need it. Part 1's job is to make **"what's free for these dates?"** an answer a superintendent can act on without calling the yard to double-check — which today's code cannot deliver, as shown below.

## Correct overlap semantics, statuses, and date normalization (the core fix)

This isn't really a multi-option design decision — it's a bug fix with one obviously correct answer — so no Options section here; stated plainly instead:

- **Overlap test**: `booking.start < query.end AND booking.end > query.start` (strict inequalities — a booking that ends exactly when the query starts, or vice versa, does **not** conflict; this matches what scenarios 10/11 showed happening today, just for the wrong reason).
- **Status filter**: exclude `status='cancelled'` unconditionally (A2). Include `confirmed` and `tentative` per A1's default, tagging which in the response.
- **Normalization**: on read, parse all 4 observed formats into a single comparable instant, applying `sites.timezone` to naive values per A3, before running the overlap test. Do this once, in one function, covered by unit tests against the specific booking IDs in the evidence table (not just happy-path dates).
- **Asset-tag join**: normalize both sides (`equipment.asset_tag`, `bookings.asset_tag`) via A4's rule before joining; log (don't silently drop) anything that still fails to match.
- **One overlap function, used twice.** The inherited bug (row 1) exists because the containment check was written once, wrong, in one place. Step 7's FleetCare maintenance-window check **must call the same overlap-test function** defined here for bookings — not a second, separately-written comparison. Writing an independent overlap check for maintenance windows is how this exact bug reappears under a different name. This is a hard requirement on step 7, not a style preference.

## FleetCare degraded-mode decision

**Options considered:**

1. **Call FleetCare synchronously per availability request.** Simplest to write; directly violates "behave sensibly when FleetCare is slow/down/rate-limited" — a single slow request (measured up to 5s, or a 30s hang) becomes Marcus's page load.
2. **TTL cache, lazily refreshed via the `/v1/maintenance/batch` endpoint (max 25 tags/call → 3 calls for 60 assets), bounded per-call timeout, no synchronous retry, serve last-known-good on failure, mark data explicitly stale past a threshold.**
3. **Background poller/circuit-breaker**, refreshing independently of the request path with exponential backoff on repeated failures. Most robust, more code than 4 hours affords alongside everything else in scope.

**Chosen: Option 2**, with concrete defaults (tune later, these are two config constants, not an architecture):
- Cache TTL: 5 minutes (maintenance windows are planned days ahead; this is nowhere near FleetCare's 20req/10s limit — 3 calls per refresh).
- Per-call client timeout: 3s (comfortably above the mock's measured 2.5–5s "slow" case most of the time, well below the 30s hang case — bounded, as required).
- No synchronous retry on failure (fail fast, serve cache).

**Revised after review (this is now a blocking spec, not an open seam):** the first version of this plan added a separate `maintenance.status` field and left it to *some future consumer* to combine it with `available`. A skeptical review correctly flagged that as the same failure mode this whole plan exists to fix, just moved one layer down — if nothing is ever wired up to read `maintenance.status`, equipment with unknown or in-maintenance FleetCare data renders as a plain green `available:true`, which is Dana's complaint, reproduced by the fix itself. Closing it at the data model, not by convention:

- **`available` is computed as `bookingAvailable AND maintenance.status == "ok"`.** `maintenance.status` is not a side channel a consumer can forget to check — it's baked into the one boolean the frontend already renders. `in_maintenance` and `unknown` both force `available:false`.
- `maintenance: {status: "ok"|"in_maintenance"|"unknown", as_of: <timestamp>}` is still returned alongside, for detail/debugging (e.g. so the UI can distinguish "actually booked" from "maintenance data unknown" in its copy), but it is no longer the only thing standing between a user and a false "available."
- **Cold start is explicitly "unknown," never "ok."** Before the cache has ever been successfully populated (server just started, or restarted mid-demo), there is no last-known-good to fall back to. The initial/zero-value state of the cache **must** be `"unknown"`, not an empty-but-valid-looking maintenance list — an uninitialized cache that defaults to "no windows found" is indistinguishable from "confirmed clean" and fails open exactly like the inherited bug. This is a required, explicitly tested state, not an edge case left to whatever the zero-value happens to be.
- This is intentionally conservative: equipment shows unavailable while maintenance data is merely unknown, even though it's probably fine. That's the correct bias given what this plan is for — Dana's complaint is about false *positives* on "available," not false negatives on "unavailable."

## Role/site visibility — authorization boundaries to enforce

Per A5/A6 (pending sign-off): the handler must read `UserFrom(r)` and apply, in order:
1. Reject if no valid, signature-verified token (fixes row 7).
2. Compute availability fleet-wide (booking + FleetCare logic unchanged by role) using the combined `available`/`maintenance.status` rule above.
3. For each item with a conflict, include full `conflict` detail only if `user.role == ops_director` **or** (`user.role in {superintendent, foreman}` **and** `conflict.site_id in user.site_ids`). `safety_manager` does **not** get a role-based bypass here, regardless of its `["*"]` site list — it's evaluated the same way a foreman would be. Otherwise, return `conflict: {exists: true}` with no site/operator/time detail.
4. Strip `daily_rate_usd` from every equipment item unless `user.role in {ops_director, superintendent}`.
5. Never include any operator field in any response (A6) — not even for roles that can see full conflict detail; that's a different endpoint if it's ever needed.
